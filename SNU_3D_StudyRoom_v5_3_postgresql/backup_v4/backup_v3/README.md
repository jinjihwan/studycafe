# SNU Library Inspired — 온라인 3D 스터디룸 v3 (v2 안정화)

> 사진으로부터 절차적으로 만든 **비공식 도서관 3D 프로젝트**입니다. 서울대학교 공식 웹사이트나 실측 디지털 트윈이 아닙니다.

**주요 원칙:** 기존 v2의 Three.js 공간, 가구, 캐릭터와 후드티, 카메라, A* 클릭 이동, NPC, 좌석 선택/착석, 머리 위 닉네임·공부시간·채팅 UI를 삭제하거나 재디자인하지 않았습니다. v3는 **서버 타이머 단일화, 연결 복구 및 전송 계층 보안 보강, 성능 진단, 회귀 테스트**가 핵심입니다.

## 준비 및 실행

Node.js **22 이상**과 인터넷 연결이 필요합니다. Three.js v0.161.0/OrbitControls는 기존과 동일하게 jsDelivr CDN에서 가져옵니다. 이 ZIP에는 CDN 라이브러리를 포함하지 않았습니다. `npm install`은 필요하지 않습니다.

1. ZIP 압축을 풀고 `SNU_3D_StudyRoom_v3_stabilized` 폴더를 엽니다.
2. Windows는 `start_server.bat`, macOS/Linux는 `./start_server.sh`를 실행합니다. 또는 터미널에서:

   ```bash
   node server/index.js
   # 또는 npm start
   ```

3. PC 브라우저에서 `http://localhost:3000/?room=main`을 엽니다. **`file://index.html`로는 실행하지 마세요.**
4. 스마트폰은 PC와 같은 Wi-Fi에 연결한 뒤 `http://PC_IP:3000/?room=main`으로 접속합니다. 예: `http://192.168.0.15:3000/?room=main`. PC의 방화벽에서 TCP 3000 포트를 허용해야 할 수 있습니다.
5. PC와 스마트폰을 **서로 다른 게스트**로 입장시키면 실제 접속자 수 2명/NPC 8명 표시와 이동·채팅·좌석 경합을 확인할 수 있습니다. 같은 브라우저 프로필의 일반 탭 2개는 게스트 토큰을 공유하여 기존 탭을 교체합니다. 일반 창과 시크릿 창, 또는 별도 기기를 사용하세요.

공간: 책상 88개, 의자 352개, NPC 8명. 좌석·NPC 번호 생성 코드는 v2와 동일합니다. **서버는 NPC를 실제 이용자 수에 포함하지 않습니다.**

## v3 핵심 수정 사항

### 서버 기준 공부 타이머

- **브라우저 localStorage에는 캐릭터 설정만 저장**합니다. 과거 v1/v2 로컬 공부 시간을 서버 총합에 더하지 않습니다.
- 서버가 한국시간(Asia/Seoul) 날짜별 누적 시간을 계산합니다. 착석 시 자동 시작, `일시정지/재개`는 서버에서 확인, 기립 시 정지합니다. 서버는 1초 간격으로 공부 시간과 날짜를 브로드캐스트합니다.
- 클라이언트 UI는 받은 누적 시간의 표시만 `performance.now()`로 보간합니다. 브라우저 탭이 숨겨져도 **클라이언트만 따로 타이머를 멈추지 않습니다.** WebSocket이 유지되면 서버에서는 정상적으로 누적됩니다.
- 모바일 앱 전환·화면 잠금 이후 탭을 다시 보이면 `sync` 상태 조회를 요청합니다. 연결이 중단된 경우 서버는 타이머를 **일시정지**하고, 좌석은 **20초간 유예** 후 회수합니다. 유예 중 동일 게스트 토큰으로 재접속하면 자리와 누적 시간이 복구되지만 **일시정지 상태로 유지**됩니다. 다시 공부하려면 `재개`를 누르세요.
- 서버가 재시작되면 메모리 기반의 공부 기록·좌석·방 상태는 초기화됩니다. 영구 저장 DB는 **미구현**입니다. 자정 이후 공부 기록은 서버 기준 한국 날짜로 다시 0부터 시작합니다.

### WebSocket / 인증 / 좌석 보호

- 게스트 토큰은 서버가 HMAC 서명하고 검증합니다. 서명이 틀린 토큰, 잘못된 방 이름, 범위 밖 이동, NPC 전용 좌석은 거절합니다. 토큰은 **보관 및 전송에 주의가 필요한 인증 정보**입니다.
- 동일 사용자의 다른 접속은 기존 연결을 교체합니다. 방당 최대 64명 접속을 지원하며 각 방의 좌석 잠금과 채팅은 분리됩니다.
- 서버가 의자 **예약→도착 확인→착석 확정** 순서를 검증하고, 예약 중 및 착석 중 동시 점유를 거부합니다. 예약은 최대 90초, 연결 종료 후 점유 정리는 약 20초+타이머 틱 오차입니다.
- Origin 검증: 웹 브라우저의 HTTP POST 및 WebSocket 업그레이드에 동일 출처 검사. `STUDYROOM_PUBLIC_ORIGIN` 환경변수로 공개 프록시 도메인을 지정할 수 있습니다. **Origin 헤더가 없는 비브라우저 클라이언트는 허용**하지만 유효한 서명 토큰을 요구합니다. 신뢰할 수 없는 외부 공개 환경에서는 방화벽·프록시·추가 인증이 필요합니다.
- WebSocket 프로토콜은 v2의 의존성 없는 제한적 RFC 6455 구현을 유지했습니다. `ws`를 사용하면 장기 운영의 유지보수에 유리하지만, 이번 제작 환경에서 npm 레지스트리 연결이 되지 않아 검증된 라이브러리 전환을 수행하지 못했습니다. 현 구현에 대해 **마스킹·분할 프레임·ping/pong·비정상 프레임·이진 프레임 거부·메시지 크기·속도 제한 테스트**를 추가했습니다. `ws`로 전환했다고 주장하지 않습니다.
- WebSocket 프레임 최대 16KiB, JSON 본문 최대 4KiB, 연결당 메시지 최대 초당 35개입니다. 세션 API는 IP당 분당 60회, 업그레이드는 IP당 분당 90회 제한을 둡니다. 간단한 개발용 제한이며 대규모 공개 서비스용 DDoS 방어가 아닙니다.
- 반응 없는 연결 확인용 heartbeat, 입장 10초 타임아웃, 프런트엔드의 재접속 및 앱 복귀 시 상태 재조회가 있습니다. 브라우저가 좌석으로 이동하던 도중 백그라운드에서 멈췄다면 재조회 시 미완료 예약을 취소해 동기화 충돌을 피합니다.

### 선택적 모바일 성능 진단

기본 UI는 v2 그대로입니다. 성능 오버레이는 URL에 진단용 파라미터를 붙인 경우에만 나타납니다.

- 기본 품질 FPS 확인: `http://서버주소:3000/?room=main&perf=1`
- 선택적 저품질 비교: `http://서버주소:3000/?room=main&perf=1&quality=low`

오버레이에서 **FPS, 95백분위 프레임 간격(p95), 렌더 호출의 CPU 시간, draw calls, 삼각형 수, 픽셀 비율**을 확인합니다. 1.5초 단위 표본의 대략적 참고치입니다. `quality=low`는 픽셀 비율을 최대 1로 제한하고 그림자를 끄는 **명시적으로 선택한 경우에만** 적용되며 기본 화면은 변경하지 않습니다. 화면이 끊기면 p95가 33ms(대략 30FPS 이하) 이상인지, 저품질에서 얼마나 개선되는지, 5~10분 사용 뒤 프레임 성능이 떨어지는지 비교하세요. **이 기능은 GPU 온도나 기기 발열을 직접 측정하지 못합니다.**

## 자동 검사

```bash
npm run check   # JS 구문 + HTML 모듈 + 프로젝트 구성/로컬 import 검사
npm test        # 실제 HTTP 서버/WebSocket 소켓을 사용하는 통합/회귀 검사
```

테스트는 Node 내장 test runner를 사용하므로 별도 npm 패키지가 필요 없습니다. 테스트 내용:

- 서로 다른 3명의 WebSocket 접속, 다른 방 격리, 실제 채팅, 유효/무효 이동 동기화
- 좌석 경합과 NPC 좌석 차단, 예약→접근→착석, 일시정지, 재연결과 좌석 회수
- 서버 시간의 증가·정지·재개, WebSocket 유지 중 브라우저 렌더링 중단에 해당하는 대기, 한국시간 자정 초기화
- 다른 Origin의 HTTP/WS 요청 차단, 잘못된 핸드셰이크, 지나치게 큰 메시지, 이진 메시지, 초당 과도한 전송
- WebSocket 마스크·분할 텍스트·중간 ping/pong·마스킹 없는 프레임 거절

실제 테스트 결과와 검증하지 못한 사항은 `TEST_REPORT.md`, 실행 로그는 `test-results.txt`를 참고하세요.

## 2대의 실제 기기에서 확인할 시나리오

1. PC와 휴대폰에서 같은 `?room=main`으로 들어가 상단에 **실제 접속자 2명 · NPC 8명**이 표시되는지 확인합니다.
2. 두 캐릭터의 이동이 반대편 화면에 나타나는지, 서로 다른 좌석에 앉을 수 있는지 확인합니다.
3. **동일 좌석을 거의 동시에 클릭**해 두 번째 사용자의 착석이 거부되는지 확인합니다.
4. 채팅을 전송해 두 화면에 머리 위 말풍선이 약 5초 나타나는지 확인합니다.
5. A가 착석한 상태로 화면 잠금/다른 앱 전환 후 1분 정도 지나 다시 복귀합니다. 네트워크 연결이 계속 유지됐다면 서버 공부 시간이 계속 증가해야 합니다. 연결이 끊겼다면 유예 시간 내 재접속 시 일시정지된 시간이 복구되고, 유예 후에는 좌석을 다른 사용자가 사용할 수 있어야 합니다.
6. 양쪽에서 `&perf=1`을 붙여 프레임 정보가 나타나는지, 5~10분 경과 시 프레임 하락이나 화면 발열 체감이 있는지 비교합니다.

실제 기기·OS마다 백그라운드 소켓 정책이 다르므로 위 결과는 직접 확인해야 합니다.

## 휴대폰만으로 서버 배포 및 테스트

**Node.js 서버가 필요하므로 HTML 파일만 정적 호스팅하면 멀티플레이어가 작동하지 않습니다.** PC가 없어도 클라우드 Linux 개발 환경에서 실행할 수 있습니다.

가능한 경로의 하나는 [GitHub Codespaces](https://github.com/codespaces) (사용 가능한 계정 및 리소스 필요)입니다.

1. 휴대폰 브라우저에서 이 ZIP을 다운로드합니다. GitHub에 빈 저장소를 만든 뒤 저장소의 **Code → Codespaces → Create codespace**를 선택해 브라우저 개발 환경을 엽니다. 화면이 좁으면 브라우저의 **데스크톱 사이트 보기**를 사용합니다.
2. Codespaces의 Explorer 폴더 컨텍스트 메뉴에서 **Upload...**를 눌러 ZIP을 업로드한 뒤 터미널에서 `unzip SNU_3D_StudyRoom_Stabilized_v3.zip`으로 풉니다. `cd SNU_3D_StudyRoom_v3_stabilized`로 이동합니다.
3. `npm run check`, `npm test`, `npm start`를 실행합니다. Codespaces에서 Node 22 이상이 아닌 경우 적절한 Node 환경을 선택해야 합니다.
4. **PORTS** 탭에서 포트 `3000`을 전달합니다. 기본 private 링크는 계정 인증이 필요합니다. 다른 휴대폰에서도 접속할 경우 포트 가시성을 **Public**으로 전환해야 할 수 있습니다. 이는 URL을 아는 누구에게나 공개되므로 테스트에 한정하세요.
5. 전달된 `https://...app.github.dev` 주소 뒤에 `/?room=main&perf=1`을 붙여 접속합니다. 친구에게 동일 링크를 공유합니다. **Codespaces의 `localhost:3000`은 휴대폰 브라우저 주소가 아닙니다.** 외부 링크는 Ports 화면에 나온 정확한 URL을 사용하세요.
6. Origin 오류가 나타나면 Codespaces 터미널에서 앱을 중지한 뒤 실제 외부 주소를 넣어 `STUDYROOM_PUBLIC_ORIGIN=https://<Codespaces의_실제_호스트> npm start`로 재실행합니다. 공개 포트 및 WebSocket 업그레이드를 지원하는 환경이어야 합니다.

Codespaces의 포트 전달·공유 절차: https://docs.github.com/en/codespaces/developing-in-a-codespace/forwarding-ports-in-your-codespace

주의: Codespaces는 영구적인 24시간 호스팅이 아닙니다. 비활성화/중단 시 서버가 멈춥니다. **24시간 서비스 운영**에는 별도 상시 Node.js 호스팅과 DB가 필요합니다.

## 반드시 알아야 할 제한

- 기존 Three.js CDN 의존성이 있습니다. 브라우저가 외부 CDN을 못 받으면 3D 공간이 뜨지 않습니다.
- 서버는 **단일 프로세스 메모리 기반**으로, 서버가 재시작되면 공부 기록 및 좌석이 사라집니다. 계정/DB/영속성은 구현하지 않았습니다.
- NPC는 각 브라우저가 로컬로 행동을 시뮬레이션합니다. NPC의 애니메이션은 서버와 동기화되지 않습니다.
- 공개 배포에는 HTTPS/WSS, 유지보수되는 WebSocket 라이브러리 검토, API 접근 제어 강화, 계정/DB, 모니터링, 프록시 검증, 배포 플랫폼 적합성 검증이 추가로 필요합니다.
- 초대 링크는 **방 주소 공유**이지 비공개 접근 권한이 아닙니다.
