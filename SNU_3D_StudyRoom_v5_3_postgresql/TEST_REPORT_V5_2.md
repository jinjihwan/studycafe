# v5.2 배포 준비 검증 보고서

## 범위

기존 v5.1의 3D 렌더링, 동물 아바타, NPC, 카메라·이동, WebSocket, Firebase Google 인증, 게스트, 공부 시간, 날짜별 기록, 친구 신청·수락·차단, 친구 랭킹과 방 권한을 보존. 서버 영구 저장 경로 분리와 SQLite 백업·이전·복원 스크립트를 추가함.

## 실제 실행한 검사

- `npm run check`: 성공 (서버/클라이언트 JS 구문, HTML 스크립트, 프로젝트 파일 검사).
- `npm test`: **40개 통과 / 실패 0개**. 기존 v5.1 회귀 테스트 36개 + 신규 배포 저장 테스트 4개.
- 신규 검사:
  1. 영구 DB·기존 인증키 누락 상태에서 운영 배포를 거부하고 기존 로컬 경로를 보존.
  2. 실제 SQLite WAL 데이터, 날짜별 공부 기록, Google UID 연결, 친구 관계, `.guest-secret`을 한 번에 백업. 백업 무결성 및 보관 개수 검증.
  3. Codespaces 내보내기 실행으로 Git 작업 디렉터리 밖에 유효한 DB·서명키 파일 저장.
  4. 서버 중지가 확인되지 않은 복원을 거부하고, 중지 확인 후 복원·롤백 백업 실행.
- 테스트용 데이터로 실제 Node.js 서버를 구동하여 `GET /health` 응답 HTTP 200, `POST /api/session` 응답 HTTP 200, `npm run backup`으로 생성된 SQLite 파일 및 서명키 쌍을 확인함.
- WAL-mode 임시 무결성 검사에서 불필요한 `*.partial-wal` 및 `*.partial-shm` 파일이 남는 문제를 발견해 청소 로직 추가 후 재검사.

## 이 환경에서 검증하지 못한 항목

- Railway 계정·유료 요금제·볼륨 실제 생성 및 장기간 운영.
- Railway Volume 파일 업로드 및 플랫폼 정기 백업 활성화의 실제 사용자 계정에서의 결과.
- 사용자 Codespaces의 실데이터 이전, 친구 관계 및 기록 건수 비교.
- Firebase 실제 서비스 계정 기반 Google 로그인 및 공개 `up.railway.app` 도메인 인증.
- 실제 스마트폰 렌더링·배터리·발열 및 다수 동시 접속 부하.
- 24시간 무중단 SLA, 다중 인스턴스 분산, 볼륨 재해 복구 실습.

## 남은 운영 리스크

- Railway Volume은 하나의 서비스 인스턴스에 연결되는 영구 볼륨이다. 재배포 시 기존 WebSocket 연결이 잠시 끊어질 수 있다.
- 6시간 간격 앱 스냅샷과 Railway 볼륨 백업의 복원 시점 이후 기록은 일부 소실될 수 있다. 운영자가 복구 시점과 장애 복구 목표(RPO/RTO)를 결정해야 한다.
- 동일 Codespaces DB를 Railway에 복사한 다음 양쪽 서버에서 계속 이용하면 **각자 별도의 DB로 기록이 갈라진다**. 이전 후에는 새 서비스만 실사용하도록 안내해야 한다.
- Firebase UID가 같으면 기존 계정 기록을 조회할 수 있지만, **게스트 토큰(localStorage)은 출처별로 분리되므로 새 도메인에 자동 이전되지 않는다**. 게스트 사용자는 이전 전 Google 계정으로 연결하는 것을 권장한다.
- Railway 볼륨 내 앱 스냅샷은 프로젝트 삭제·계정 유실에 대비한 독립적인 오프사이트 백업이 아니다. 주기적 외부 다운로드와 복원 검증 필요.
- 2026년 현재 코드의 Firebase Google 로그인은 모바일 팝업 방식을 기본으로 하므로 모바일 브라우저에 따라 팝업 허용이 필요할 수 있다. Firebase Redirect 흐름은 별도의 저장소·도메인 설정 검증이 필요하다.
